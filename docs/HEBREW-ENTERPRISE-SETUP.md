# SmartQ — מדריך הקמה, SSO ועלייה לייצור

המדריך מרכז את ההגדרות הדרושות להפעלת SmartQ בסביבת לקוח, בדיקות כניסה, עברית ו-Entra ID. הוא מתייחס למימוש הקיים במאגר; הוא אינו מחליף בדיקת אבטחה, בדיקת שחזור או אימות מול סביבת הייצור של הלקוח.

## 1. מה צריך לפני ההקמה

- פרויקט Supabase נפרד לכל סביבת ייצור, או מודל רב־ארגוני עם גיבויים, הרשאות ותהליכי שחזור שנבדקו.
- פרויקט Vercel (או שרת Next.js תואם) עם כתובת HTTPS קבועה לכל סביבה.
- Node.js 20.9 ומעלה לפיתוח מקומי (Next.js 16); Vercel מנהלת את runtime בפריסה.
- מפתח Supabase מסוג `service_role` שנשמר במשתני שרת בלבד.
- `SESSION_SECRET` — מפתח חתימה פנימי של האפליקציה. חובה; יוצרים אותו פעם אחת לכל סביבה בעזרת הפקודה שבהמשך.
- `IDP_ENCRYPTION_KEY` — לא נדרש להפעלה הרגילה או להדגמה. מוסיפים אותו רק אם מנהל ארגון שומר ב-SmartQ Client Secret פרטי משלו ל-OIDC.
- מפתח Gemini אם רוצים להפעיל AI בארגוני לקוחות. הסימולציה הציבורית וסביבת ההדגמה אינן דורשות Gemini.
- איש קשר ארגוני שיקבל את חשבון המנהל הראשי של הארגון.

אין לשתף בין לקוחות סיסמאות מנהל, מפתחות חתימה, מפתחות Supabase או סודות Entra.

## 2. משתני סביבה

להגדיר כל ערך גם מקומית ב-`.env.local` וגם בהגדרות הסביבה המתאימות ב-Vercel. לא להכניס ערכים אמיתיים ל-Git.

| משתנה | חובה | שימוש |
|---|---:|---|
| `NEXT_PUBLIC_SUPABASE_URL` | כן | כתובת פרויקט Supabase |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | כן | מפתח ציבורי; השרת לא משתמש בו בפרודקשן |
| `SUPABASE_SERVICE_ROLE_KEY` | כן בפרודקשן | גישת שרת למסד הנתונים; סוד שרת בלבד, ללא `NEXT_PUBLIC_` |
| `SESSION_SECRET` | כן בפרודקשן | מפתח פנימי לחתימת כניסות. לפחות 32 תווים אקראיים; לא סיסמת משתמש |
| `IDP_ENCRYPTION_KEY` | לא, אלא אם משתמשים ב-OIDC עם פרטי לקוח נפרדים | מצפין Client Secret של IdP שמנהל הארגון מזין. נדרש רק לתרחיש הזה; מפתח base64 של 32 bytes |
| `OIDC_CLIENT_ID` | אופציונלי | Client ID של App Registration רב־ארגוני המנוהל על ידי SmartQ |
| `OIDC_CLIENT_SECRET` | אופציונלי | סוד שרת של App Registration רב־ארגוני; יחד עם ה-Client ID, נשמר ב-Vercel בלבד |
| `PLATFORM_BOOTSTRAP_EMAIL` | בהקמה ראשונה | כתובת מנהל SmartQ הראשוני של קונסולת הספק |
| `PLATFORM_BOOTSTRAP_PASSWORD` | בהקמה ראשונה | סיסמה ארוכה וייחודית למנהל הראשוני; להסיר לאחר יצירת מנהל ספק קבוע |
| `GEMINI_API_KEY` | אם מפעילים AI | מפתח שרת לשירות Gemini; לא לחשוף לדפדפן |
| `GEMINI_MODEL` | לא | שינוי דגם ברירת המחדל, אם נדרש |
| `RESEND_API_KEY` | כן לטופס יצירת קשר | מפתח API של Resend; משתנה שרת בלבד |
| `RESEND_FROM_EMAIL` | כן לטופס יצירת קשר | כתובת שולח מאומתת ב-Resend, למשל `SmartQ <contact@example.com>` |
| `CONTACT_TO_EMAIL` | כן לטופס יצירת קשר | תיבת הדואר שאליה יגיעו פניות מהאתר |
| `NEXT_PUBLIC_APP_URL` | כן בפרודקשן | כתובת HTTPS הבסיסית המדויקת, למשל `https://support.example.co.il`; נדרשת ל-callbacks ול-metadata של SSO |
| `DEMO_ENABLED` | לא | `false` מכבה את סביבת ההדגמה הציבורית |

### יצירת `SESSION_SECRET` (חובה)

זהו מפתח אבטחה פנימי של השרת, לא משהו שצריך לזכור או להקליד בכניסה. צרו אותו פעם אחת והעתיקו את הפלט לשדה `SESSION_SECRET` ב-Vercel (ול-`.env.local` בפיתוח מקומי). שמרו על ערך קבוע; החלפתו תנתק משתמשים מכל הסשנים הפעילים.

```powershell
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64'))"
```

### `IDP_ENCRYPTION_KEY` (אופציונלי)

אפשר להשאיר את המשתנה הזה לא מוגדר כרגע. צריך ליצור ולהגדיר אותו רק אם ארגון בוחר להזין Client ID ו-Client Secret משלו במסך הגדרות ה-SSO של SmartQ. שימוש ב-App Registration משותף של SmartQ, כניסה מקומית, SAML, ההדגמה והאתר אינם דורשים אותו. בלי המפתח, שמירת Client Secret פרטי של ארגון תידחה.

```powershell
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
```

הגדרת `OIDC_CLIENT_ID` ו-`OIDC_CLIENT_SECRET` היא זוג: או ששניהם מוגדרים, או ששניהם ריקים. זהו ה-client המשותף של SmartQ; מנהל ארגון יכול לבחור להשתמש בו או להזין client ID וסוד נפרדים של הארגון.

## 3. Supabase, מיגרציות והרשאות

1. הריצו את הסקריפט לקריאה בלבד [`supabase/maintenance/001_review_database.sql`](../supabase/maintenance/001_review_database.sql). בדקו אילו טבלאות ונתונים קיימים לפני כל שינוי.
2. אפשר לבדוק עמודות נדרשות בעזרת [`supabase/inspect_schema.sql`](../supabase/inspect_schema.sql). טבלאות הבסיס `tenants`, `tenant_users`, `tickets` ו-`platform_admins` חייבות להתקיים. `001_enterprise.sql` מרחיבה סכימה קיימת ואינה יוצרת אותן.
3. קחו גיבוי שניתן לשחזר, ואז הריצו ב-Supabase SQL Editor לפי הסדר את [`001_enterprise.sql`](../supabase/migrations/001_enterprise.sql) ואת [`003_oidc_sso.sql`](../supabase/migrations/003_oidc_sso.sql). אם `002_enable_rls.sql` כבר הורץ בעבר, אין צורך לבטל RLS; `003_oidc_sso.sql` בטוחה להרצה גם במצב זה.
4. הוסיפו ב-Vercel את משתני Supabase ואת `SESSION_SECRET`. הוסיפו `IDP_ENCRYPTION_KEY` רק אם תאפשרו לארגונים לשמור Client Secret פרטי ל-OIDC. מפתחות שרת אינם יכולים להתחיל ב-`NEXT_PUBLIC_`.
5. פרסו מחדש ובדקו `GET /api/health`. נדרשת תשובה `200` עם `status: "ok"` ו-`database: "ok"`.
6. בדקו כניסת מנהל, עובד וטכנאי, פתיחה וטיפול בקריאה, שינוי סיסמה, והגדרות SSO בשני הפרוטוקולים.
7. רק אחרי בדיקת הגישה, הריצו [`002_enable_rls.sql`](../supabase/migrations/002_enable_rls.sql). המיגרציה חוסמת גישת `anon`/`authenticated` ישירה; השרת משתמש ב-`service_role`.
8. בדקו שוב את כל התהליכים ואת `GET /api/health`.

אם `SUPABASE_SERVICE_ROLE_KEY` חסר בפרודקשן, האפליקציה נכשלת במפורש במקום לנסות להשתמש במפתח הציבורי. אם כניסה נכשלת לאחר מיגרציה, בדקו לוגי שרת, הרשאות מפתח השירות, עמודות חסרות ומצב החשבון לפני איפוס סיסמה.

**הקמה של מסד נתונים חדש:** המיגרציה `001_enterprise.sql` אינה יצירת schema מלאה; היא מניחה שטבלאות הבסיס כבר קיימות. אין במאגר כרגע migration מלא לבניית טבלאות הבסיס מאפס. אם ה-Supabase חדש או שטבלאות הבסיס חסרות, עצרו לפני הרצת המיגרציה ואל תיצרו schema מאולתר; נדרשת קודם הגדרת schema בסיסית ומאושרת.

### ניקוי טבלאות שאינן בשימוש

הקוד והמיגרציות הנוכחיים משתמשים בשמונה טבלאות ב-`public`:

`tenants`, `tenant_users`, `tickets`, `ticket_events`, `tenant_settings`, `platform_admins`, `audit_log`, `contact_requests`.

הגיבוי והדמו נשענים על חלק מהטבלאות האלה, ולא כל שמונה הן נתוני קריאות. אין להסיק שטבלה אחרת אינה רלוונטית רק משום שלא נמצאה בקוד: ייתכן שהיא משמשת דוחות, טריגרים, פונקציות SQL, אינטגרציה חיצונית או נתוני לקוח. איני יכול לראות את סכימת Supabase שלך, ולכן לא הכנסתי שמות של טבלאות למחיקה ולא מחקתי דבר.

1. הריצו קודם את [`supabase/maintenance/001_review_database.sql`](../supabase/maintenance/001_review_database.sql) והורידו/שמרו את תוצאותיו.
2. בדקו ידנית מול `pg_cron`, Edge Functions, SQL functions, triggers, views, כלי BI, אינטגרציות והיסטוריית מיגרציות. בדיקת `DROP ... RESTRICT` מגינה על תלותי PostgreSQL, אך אינה מזהה שימוש חיצוני.
3. בצעו גיבוי לפני כל מחיקה, ואמתו שניתן לשחזר אותו.
4. רק אחרי אישור מפורש של כל טבלה, ערכו את [`supabase/maintenance/002_drop_approved_tables.sql`](../supabase/maintenance/002_drop_approved_tables.sql): הוסיפו את שמות הטבלאות המדויקים ל-`approved_tables`, שנו את `execute_cleanup` ל-`true` והזינו את מחרוזת האישור המופיעה בקובץ.
5. הסקריפט שומר על שמונה הטבלאות הנדרשות, מוגבל לסכימת `public`, ואינו משתמש ב-`CASCADE`. כל תלות DB עוצרת את המחיקה במקום להסיר אובייקטים נוספים. בדקו את ההודעות ואת התוצאות לאחר ההרצה.

אל תריצו את סקריפט המחיקה על ייצור לפני אימות הגיבוי והאישור של בעל המערכת. אם המטרה היא רק לנקות נתוני הדגמה, אל תמחקו טבלאות; בדקו את רשומות `tenant_id = 'demo'` ואת המדיניות העסקית לפני מחיקת נתונים.

## 4. ROOT וחשבונות מנהלים

יש להפריד בין שני סוגי מנהלים:

- **מנהל SmartQ (Super Admin)** מנהל את קונסולת הספק ב-`/platform`. משתמשים ב-`PLATFORM_BOOTSTRAP_EMAIL`/`PLATFORM_BOOTSTRAP_PASSWORD` רק לכניסה ראשונית. לאחר יצירת משתמש `Super Admin` קבוע, מנגנון ה-bootstrap מושבת; הסירו את משתני ה-bootstrap מפריסת הפרודקשן.
- **מנהל ארגון (Manager)** הוא חשבון השורש של סביבת הלקוח, לא חשבון-על משותף. בעת יצירת ארגון חדש דרך קונסולת הספק נוצרים חשבון מנהל וסיסמה זמנית חד-פעמית. החשבון מחויב להחליף את הסיסמה בכניסה הראשונה. שמרו את הסיסמה בערוץ מסירה מאובטח בלבד.

אין להוסיף `root/root`, סיסמה קבועה לכל לקוחות או דלת אחורית. צרו מנהל ארגון נפרד לכל לקוח, עם MFA ב-Entra ובקרת גישה לפי צורך.

במימוש הנוכחי `tenants` הוא רישום ה-Organization/Workspace, `tenant_users` הוא ספר המשתמשים והתפקידים של אותו Workspace, ו-`tenant_settings` מחזיק את הגדרות ה-SSO. קונסולת `/platform` יוצרת ארגון ומנהל ראשון; מנהל הארגון מנהל את סביבת העבודה שלו תחת `/{tenant}/manage`. מודל התוכניות, מדידת שימוש וחיוב עדיין לא ממומשים ואינם נדרשים ל-POC.

### בידוד בין ארגונים

- סשן משתמש חתום כולל `tenantId`; API מוגן קורא אותו מה-cookie המאומת ולא מקבל מזהה ארגון מהבקשה כמקור הרשאה.
- לפני כל API מוגן, `requireTenant` מאמת שהארגון עדיין קיים/פעיל ושהמשתמש עדיין פעיל ושייך לאותו `tenant_id`; התפקיד נקרא מחדש ממסד הנתונים.
- כל קריאות וכתיבות של קריאות, אירועים, משתמשים, הגדרות, סטטיסטיקות ויומן ארגוני מסוננות לפי `tenant_id` של הסשן. מזהה קריאה לבדו אינו מספיק לגישה.
- שכבת `proxy` בודקת גם שכתובת `/{tenant}/...` תואמת לארגון שבסשן, לפני הצגת דפים מוגנים. כניסה ועמוד חסימת גישה הם החריגים הציבוריים.
- מסלולי `/api/platform/*` הם ממשק ספק גלובלי ונגישים רק עם session מסוג `platform` וחשבון `platform_admins`; הם לא מסלולי לקוח.
- `002_enable_rls.sql` חוסמת גישה ישירה ממפתחות `anon`/`authenticated`. השרת משתמש ב-`service_role`, שעוקף RLS; לכן הסינון בקוד השרת הוא חלק הכרחי מהבידוד ואסור להסירו.

בדיקת קבלה: התחברו כמשתמש בארגון A ונסו לפתוח ישירות עמוד של ארגון B, לבקש מספר קריאה של B דרך `/api/tickets/{id}`, ולקרוא/לשנות משתמשים והגדרות. יש לצפות להפניה למסך כניסה, `404` או `403`, ולוודא שאין מידע או שינוי מצד B. חזרו על הבדיקה עם עובד, טכנאי ומנהל, ובדקו שממשק `/platform` נגיש רק למשתמש ספק.

## 5. כניסת משתמשים ופתרון תקלות

### כניסה מקומית

- העובד, הטכנאי והמנהל נכנסים ל-`/{tenant}/login`; בדף הבית אפשר להקליד את מזהה הארגון כדי להגיע למסך.
- התפקידים במסד הם `User`, `Admin` ו-`Manager`. `Admin` הוא טכנאי IT; `Manager` מנהל את הארגון.
- משתמשים ותיקים עם ערכי תפקיד `Technician` או `IT Technician` מזוהים כטכנאי. ערכי התפקיד במסד עדיין צריכים להיות אחידים בעתיד.
- משתמש חדש מקבל סיסמה חד-פעמית דרך ניהול המשתמשים ונדרש להחליף אותה.
- אחרי חמש סיסמאות שגויות החשבון ננעל ל-15 דקות.
- ארגון מושעה או משתמש מושבת לא יכולים להמשיך להשתמש בסשן קיים.

### בדיקות כשהכניסה לא עובדת

1. בדקו שהמזהה בכתובת תואם ל-`tenants.id` באותיות קטנות.
2. בדקו שהארגון פעיל, שהמשתמש קיים באותו `tenant_id`, שכתובת הדוא״ל נשמרה באותיות קטנות ושהחשבון פעיל.
3. בדקו את ערך `role`. לטכנאי השתמשו ב-`Admin`, למנהל ב-`Manager`, ולעובד ב-`User`.
4. אם נוצרה סיסמה זמנית, השתמשו בה והחליפו אותה כשמתבקשים.
5. עבור SSO, ודאו שהמשתמש קיים ומסומן פעיל ב-`tenant_users` של אותו ארגון. משתמשי SSO שלא הוקצו מראש ב-SmartQ נחסמים; אין כרגע provisioning אוטומטי או SCIM.
6. בדקו שנוספו עמודות האבטחה מ-`001_enterprise.sql` ושמפתח השירות תקין.
7. בדקו את לוגי Vercel. כשל schema או מסד נתונים מוחזר ככשל שרת ולא אמור להיראות כמו סיסמה שגויה.
8. משתמשי סביבת `demo` אינם יכולים להיכנס בסיסמה; השתמשו בכפתורי הדמו בדף הבית.

## 6. Microsoft Entra ID

SmartQ תומכת בכניסת משתמשים עם **OpenID Connect (Authorization Code + PKCE)** וב-**SAML 2.0**. ארגון יכול להפעיל אחד מהם או את שניהם. אלה פרוטוקולי כניסה: התפקידים ב-SmartQ מנוהלים בנפרד דרך ניהול המשתמשים של הארגון (`Manager`, `Admin` לטכנאי, `User` לעובד). אין תלות בהקצאת קבוצות Entra, ואין לבלבל בין App Registration של OIDC ל-Enterprise Application של SAML.

### אפשרות מומלצת: App Registration רב־ארגוני של SmartQ

במודל SaaS רגיל SmartQ מחזיקה App Registration אחת מסוג Web, בוחרת **Accounts in any organizational directory**, ומגדירה Redirect URI:

`https://<כתובת-הייצור>/api/auth/oidc/callback`

1. הוסיפו את ה-Client ID ואת ה-Client Secret של SmartQ כמשתני שרת ב-Vercel: `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`. השתמשו ב-Secret לפי מדיניות הארגון, הגדירו תאריך תפוגה ורוטציה. אימות באמצעות תעודה עדיין אינו ממומש.
2. אל תבקשו הרשאות Microsoft Graph אם המוצר צריך רק כניסה. ה-scopes במימוש הם `openid email profile`.
3. הלקוח מגדיר ב-SmartQ את ה-Issuer המדויק של ה-directory שלו, לדוגמה `https://login.microsoftonline.com/<tenant-id>/v2.0`. אין להשתמש ב-`common` או ב-`organizations` בתור Issuer של ארגון, כדי למנוע ערבוב זהויות בין tenants.
4. אם מדיניות הלקוח מחייבת, מנהל Entra מאשר את האפליקציה/ה-consent. הלקוח אינו צריך רישום או Client Secret משלו במצב זה.
5. ודאו ש-Service Principal נוצר ב-tenant של הלקוח. אין צורך להגדיר group assignment כדי לקבל תפקידים ב-SmartQ; מנהל הלקוח מקצה משתמשים ותפקידים בתוך ה-Workspace. אם `Assignment required` מופעל ב-Enterprise Application של הלקוח, יש להקצות משתמשים באופן פרטני או לשנות את המדיניות לפי החלטת מנהל Entra.
6. המשתמש חייב להתקיים כמשתמש פעיל ב-SmartQ באותו ארגון. האפליקציה משווה claim של `email`, `preferred_username` או `upn` לכתובת שהוקצתה; `email_verified=false` נדחה.

### אפשרות חלופית: הלקוח מביא OIDC client משלו

מנהל הארגון יכול להגדיר Issuer, Client ID ו-Client Secret משלו. יש לרשום את Redirect URI המדויק שמוצג במסך SSO, להפעיל Authorization Code Flow ולהגדיר את ה-scopes `openid email profile`. ה-secret מוצפן בשרת ב-AES-256-GCM; ה-API לעולם לא מחזיר אותו למסך. לתרחיש הזה בלבד יש להגדיר `IDP_ENCRYPTION_KEY` בכל סביבה. אם משתמשים ב-App Registration המשותף של SmartQ, אין צורך במפתח הזה.

המימוש קורא את OIDC discovery metadata מתוך ה-Issuer; אין שדות לעריכה ידנית של authorization/token/JWKS URLs. נדרשים HTTPS, כתובות ציבוריות ומסמך discovery תקין. הקוד בודק כתובות DNS ציבוריות, משתמש בתוצאת DNS שנבדקה גם בחיבור עצמו כדי לצמצם DNS rebinding, חוסם redirects, מגביל זמן ותשובות ל-1 MiB. יש להפעיל בנוסף מדיניות egress ברמת התשתית כאשר ספק האירוח מאפשר זאת; בדיקות האפליקציה אינן תחליף להגנה שכבתית ברשת.

### הגדרת SAML 2.0

1. היכנסו לארגון כ-`Manager` ופתחו את הגדרות SSO.
2. השתמשו בערכי `Entity ID` ו-`Reply URL (ACS)` שהמערכת מציגה; הם מבוססים על `NEXT_PUBLIC_APP_URL`.
3. הגדירו אותם ב-IdP כ-SP identifier ו-ACS, ודרשו חתימת Assertion.
4. הזינו Login URL ותעודת חתימה ציבורית (PEM/Base64). SmartQ מאמתת את חתימת ה-Assertion, audience וחלון התוקף.
5. הפעילו SAML רק לאחר שמירת כל הערכים ובדקו מול משתמש ניסוי. אין צורך ב-Group claim לשיוך תפקידים.
6. הקימו מראש משתמשים פעילים ב-SmartQ. ערכי התפקיד ב-Workspace הם מקור ההרשאה; משתמש שלא נמצא או מושבת ב-SmartQ נחסם.
7. שמרו תעודות לפי תהליך הארגון והחליפו אותן לפני תאריך התפוגה.

### מה עדיין מחוץ ל-POC

אין כרגע SCIM/JIT provisioning, מיפוי קבוצות אוטומטי, סנכרון ספרייה, איפוס סיסמה דרך IdP, חיוב או אכיפת תוכניות רישוי. מנהל SmartQ יוצר Organization בקונסולת `/platform`; מנהל הארגון מנהל משתמשים, תפקידים ו-SSO ב-`/{tenant}/manage`. מימושי רישוי/חיוב יתווספו בנפרד ולא ישנו את מודל הזהויות.

## 7. עברית, RTL ונגישות

- ברירת המחדל היא `he`, והמסמך הראשי מסומן `lang="he"` ו-`dir="rtl"`. מעבר שפה חייב להחליף גם כיוון ל-`ltr`.
- בדקו בכל מסך את סדר הפעולות, טבלאות, תפריטים, מודלים, טוסטים, הודעות שגיאה, מקלדת ומסכים קטנים.
- שמרו טקסט עברי ב-Unicode/UTF-8. אל תבצעו היפוך ידני של מחרוזות או של סדר נתונים.
- כתובות דוא״ל, מזהי ארגון, כתובות URL, קודי קריאה ומחרוזות טכניות (למשל `VPN`, `Entra ID`, `SLA`) מוצגים ב-LTR מקומי; בדקו שילוב עברית/אנגלית באותה שורה.
- סיווגי AI, שאלות הבהרה, כותרות קריאה והודעות אישור צריכים לחזור בעברית כששפת המשתמש עברית. בדקו גם ניסוח, מין/רבים, תאריכים ואזור זמן `Asia/Jerusalem`.
- ודאו גופן עברי תקין, ניגודיות, ניווט מקלדת, שמות נגישים לשדות והודעות סטטוס לקורא מסך.
- בדקו בדפדפנים ובמכשירים שבהם העובדים משתמשים בפועל, לרבות תצוגת מובייל והדפסה אם רלוונטי.

## 8. בדיקות לפני לקוח

- הריצו `npm run lint`, `npm run typecheck` ו-`npm run build`.
- בדקו כניסה/יציאה, שינוי סיסמה, חסימת חשבון, שינוי/השבתת משתמש, בדיקת הרשאות לכל תפקיד, בידוד בין ארגונים, פתיחת קריאה, הקצאה, סגירה, SLA ויומן ביקורת.
- בדקו כניסה ב-OIDC וב-SAML בסביבת ניסוי, state/nonce/PKCE, משתמש לא מוקצה, משתמש מושבת, תפקידים מקומיים וסבב החלפת סוד/תעודה.
- בדקו בפועל בידוד A/B לפי תת-הסעיף לעיל, כולל קריאת API ישירה עם מזהה קריאה מארגון אחר.
- ודאו שאין סודות ב-Git, בלוגים או בדפדפן. בדקו את headers ואת הגדרות HTTPS בדומיין.
- הגדירו גיבויים, בדיקת שחזור, ניטור, התראות, מדיניות שמירת יומנים ותגובה לאירוע.
- לפני הרחבה, העבירו rate limiting של מסלולים ציבוריים (כולל הדמו) למנגנון משותף בין מופעי שרת, ולא רק לזיכרון של מופע יחיד.
- סימולציית הצ׳אט בדף הבית וסביבת העבודה הציבורית משתמשות בתשובות קבועות ובסיווג מקומי; הן אינן קוראות ל-Gemini. בדף הבית גם לא נוצרת קריאה אמיתית, אך בסביבת ההדגמה נוצרות קריאות ב-Workspace של `demo`. עדיין יש להתייחס לכל קלט ציבורי כמידע שנשלח לשרת SmartQ.
- אשרו עם הלקוח דרישות פרטיות, מיקום נתונים, תקופת שמירה, הסכמי עיבוד נתונים, MFA ו-SLA תפעולי.

## 9. אינטגרציות חיצוניות

- **Supabase/Postgres:** פרויקט, מפתחות, גיבוי, מיגרציות והרשאות RLS לפי סעיף 3. המפתח `service_role` שמור בשרת.
- **Vercel/דומיין:** הגדרת משתני סביבה לכל `Development`/`Preview`/`Production`, דומיין HTTPS, `NEXT_PUBLIC_APP_URL` תואם בדיוק לכתובת הייצור, פריסה מחדש ובדיקת `/api/health`.
- **Google Gemini:** יצירת API key והגדרתו ב-`GEMINI_API_KEY` כמפתח שרת; לוודא מכסות, חיוב, פרטיות נתונים, הרשאות ותגובה למצב שבו הספק אינו זמין. רק משתמשים מחוברים לארגון שאינו `demo` מפעילים את Gemini דרך עוזר הקריאות.
- **Microsoft Entra / IdP:** OIDC דרך App Registration רב־ארגוני של SmartQ או client ייעודי ללקוח; לחלופין SAML 2.0 עם Enterprise Application. הלקוח מגדיר את ה-Issuer/פרטי ה-IdP בעצמו. תפקידים נקבעים בתוך SmartQ ואינם תלויים ברישוי Group Assignment. משתמשים חייבים להיות פעילים ומוקצים מראש ב-Workspace.
- **ניטור ותפעול:** להגדיר uptime monitoring ל-`/api/health`, איסוף לוגי שרת, התראות, גיבוי/שחזור, רוטציית מפתחות ותהליך אירוע. אין אינטגרציית ניטור או גיבוי מנוהל שנוצרת אוטומטית בקוד.
- **Resend — טופס יצירת קשר:** צרו חשבון Resend, אמתו את הדומיין השולח והגדירו את רשומות ה-DNS ש-Resend מספק. הוסיפו ב-Vercel את `RESEND_API_KEY`, את `RESEND_FROM_EMAIL` בפורמט `SmartQ <כתובת-מאומתת>` ואת `CONTACT_TO_EMAIL`. המפתח הוא סוד שרת בלבד; אין לשים `NEXT_PUBLIC_` או לחשוף אותו בדפדפן. ה-API שומר את הפנייה ב-`contact_requests` ושולח הודעה לתיבה שהוגדרה עם אפשרות להשיב ישירות למגיש. אם Resend נכשל, הפנייה נשארת במסד והטופס מציג שגיאה במקום להציג הצלחה.
- **דוא״ל והתראות אחרות:** Resend מחובר כרגע רק לטופס יצירת קשר. לא ממומשות הודעות דוא״ל לעובדים/טכנאים על קריאות; יש לתכנן זאת בנפרד לפני הצגת היכולת ללקוחות.
- **מערכות ארגוניות נוספות:** לא נמצאה אינטגרציה ממומשת ל-ITSM חיצוני, HR/SCIM, CMDB, Teams/Slack או כלי ניטור. יש לתכנן בנפרד OAuth והרשאות מינימליות, מיפוי זהויות, טיפול בכשלים, audit, retry והפרדת נתונים לפני חיבור לכל לקוח.

השלמת הצעדים בקובץ זה אינה תעודת עמידה בתקני אבטחה או הבטחה שהמערכת מוכנה למכירה ללא בדיקות ארכיטקטורה, עומסים, התאוששות מאסון וחדירה עצמאיות.
